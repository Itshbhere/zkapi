This construction uses classical elliptic-curve assumptions. Circuit ID
`zkapi-v2-note-bound-v1` identifies the current setup. The committed keys are a
single-party development setup; see `protocol/setup/v2/README.md` for its trust
and deployment compatibility requirements.

## Note binding

The full private leaf is `L = H_leaf(note_id, H_reg(secret, 0), deposit, expiry)`.
Both request and withdrawal circuits include that same leaf in the commitment.
A server-signed state cannot be reused with a different note membership path.
Rerandomization changes the blinding term while preserving the note term.

## Domain separation

Native helpers and circuits use `zkapi.v2.reg`, `zkapi.v2.leaf`,
`zkapi.v2.node`, `zkapi.v2.null`, `zkapi.v2.auth`, `zkapi.v2.state`,
`zkapi.v2.clear`, `zkapi.v2.withdraw`, `zkapi.v2.anchor`, `zkapi.v2.blind`,
and `zkapi.v2.sig`. The note generator uses
`zkapi.v2.note-binding.generator.v1`.

Canonical payload and response hashing retains its existing byte-level
encoding. The request context commits to the exact client request ID and
payload digest, and the public authorization tag binds it to the nullifier.

## Public and private inputs

Request proofs expose the protocol version, chain, vault, active root, state
signing key, request time, solvency bound, nullifier, authorization tag, and
anonymous commitment. The note identity, secret, deposit, expiry, balance,
blinding, anchor, Merkle siblings, and carried signature stay private.

Withdrawal proofs reveal the note ID, final balance, destination, nullifier,
and clearance mode along with the deployment fields, keys, active root, and
withdrawal tag. That tag binds the withdrawal terms to the consumed state.

`protocol/rust/crates/zkapi-types/src/inputs.rs` fixes the 12 request and 14
withdrawal public-field slots. The historical internal `Felt252` type name
represents a canonical BN254 scalar-field value; JSON is a checked hexadecimal
string. `zkapi-proof/src/groth16.rs` defines the actual constraints.
