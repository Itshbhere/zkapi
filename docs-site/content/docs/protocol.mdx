---
title: Protocol
description: Sequential private spending and native ETH close-out
---

Each valid request consumes one private state and yields a fresh server-signed
state. A shared nullifier namespace covers API requests and withdrawals.

## Registration

1. The wallet samples a nonzero secret and derives its registration commitment.
2. The user calls the native vault's payable deposit function with an exact
   whole-gwei amount.
3. The vault assigns a note ID and expiry and inserts the full note leaf into
   its depth-32 tree.
4. The wallet starts with balance equal to the deposit and anchor 1.

The commitment to the private balance also includes the full membership leaf:
`E(B,r,L) = B*G + r*H + L*J`. That leaf stays fixed through every transition.

## Request

A Groth16 proof establishes membership, secret knowledge, a valid genesis or
signed state, expiry, solvency, correct rerandomization, and a nullifier bound
to the exact request context. The server verifies the public deployment fields
and proof before durably reserving the nullifier.

After usage is determined, the server applies a charge within the configured
bound and computes `E_new = E_anon - charge*G + blind_delta*H`. It derives a
fresh anchor, signs the next state with Schnorr, and persists the transition.
The wallet checks the signature and commitment update before installing it.
Idempotent recovery returns the persisted result after transport failures.

Direct OpenRouter mode authorizes a short-lived key lease. Prompt and response
traffic goes directly to OpenRouter; the billing server settles measured
usage after the lease's settlement boundary.

## Refunds

Unused funds remain in the private balance. A close-out reveals the final
balance and settles native ETH:

```text
user payout     = final balance
operator payout = deposit - final balance
```

There is no on-chain transfer for each individual API request.

## Withdrawal

For mutual close, the server reserves the current withdrawal nullifier and
issues a clearance signature. The client proves its final balance and
clearance, binding the chosen destination and clearance mode. The vault removes
the leaf and pays the user and treasury.

If clearance is unavailable, an escape proof starts the configured challenge
period and immediately removes the leaf. A previous request proof using the
same nullifier can challenge a stale escape and restore the leaf. Its historical
root remains valid evidence after unrelated tree updates. Otherwise the pending
withdrawal can be finalized after its deadline.

An active note that expires without close-out can be claimed for the treasury.
The SDK preserves deployment-bound journals and provides transaction recovery
for interrupted deposits and withdrawals.
